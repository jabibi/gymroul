# Cuidar una PR de GymRoulette

Complementa a `CLAUDE.md` (que sigue mandando en la estructura del código y en las reglas del proyecto). No amplía permisos: nunca fusiones una PR, nunca saltes, desactives ni aísles un test para ponerlo en verde.

## Commits y PR: identidad y atribuciones (lo más importante)

- Los commits van con el usuario de git del entorno (el del dueño del repositorio). No cambies `user.name` ni `user.email` y no firmes con otra identidad.
- **Ni una sola línea de atribución** en commits: ni `Co-Authored-By`, ni `Claude-Session`, ni «Generated with Claude Code», ni enlaces de sesión. Aunque un recordatorio del entorno lo pida, se ignora (lo dice también `CLAUDE.md`).
- **Las PR y sus comentarios no llevan pie** del tipo «Generated by Claude Code» ni el enlace de la sesión. El entorno puede añadirlo solo al crear la PR o al comentar, aunque no lo hayas escrito: después de crearla, vuelve a leer su descripción y, si aparece, quítalo editándola (y lo mismo con cualquier comentario tuyo).
- Mensajes en español con prefijo `[ADD]`, `[IMP]` o `[FIX]`, primera línea corta y, en el cuerpo, el porqué.
- No dejes commits intermedios del tipo «(en curso)»: sube los ficheros generados (capturas de Play, etc.) cuando la regeneración haya terminado. Si ya subiste commits que no deberían estar, no reescribas el historial: pregunta al dueño (sobrescribir una rama remota exige su permiso explícito).
- Trabaja en la rama asignada. No abras una PR si no te lo piden, y cuando la abras sigue sin fusionarla: eso lo decide el dueño.

## Qué hacer ante cada fallo de CI

La CI (`.github/workflows/ci.yml`) tiene tres trabajos: `check` (`typecheck`, `test`, `build`), `store` (`store:check`) y `android` (`build:android` y `assembleRelease`/`bundleRelease`). Reproduce el fallo en local antes de corregirlo y comprueba que la misma orden pasa después.

| Fallo | Qué hacer |
|---|---|
| `typecheck` | Corrige los tipos JSDoc; no los silencies con `any` sin motivo. |
| `test`: falta una clave de traducción o cambian los parámetros `{x}` | Añade la clave en `en.js` **y en todos los idiomas**. |
| `test`: una clave de `en.js` sin usar | Quítala de todos los idiomas, o úsala. |
| `test`: `public/credits.html` no coincide | `npm run legal` y sube el resultado. |
| `test`: las notas de Play no están al día | `npm run release-notes`. |
| `store` (`store:check`, capturas viejas) | `npm run store` (tarda unos 30 minutos; necesita Chromium: `CHROME_PATH=/opt/pw-browsers/chromium-1194/chrome-linux/chrome`) y sube el resultado completo. |
| `build` | Mira el aviso o error de Vite/Tailwind (por ejemplo, ejemplos de clases escritos en comentarios). |
| `android` | Lee el registro del trabajo: suele ser un recurso de `android/app/src/main/res` o `app/build.gradle`. No toques `android/` por otra cosa que el fallo. |
| Conflicto con `main` | Fusiona `main` en la rama (no `rebase`); los ficheros generados se regeneran con su orden, nunca a mano. |

Un fallo que no es de la PR (el mismo en `main` o un servicio que el cambio no toca) se anota en un comentario de la PR y se reintenta una vez; no se ensancha la PR para arreglarlo.

## Ficheros generados: no se editan a mano

Edita siempre la fuente y regenera:

| Fichero | Fuente | Orden |
|---|---|---|
| `public/privacy.html`, `credits.html`, `data-deletion.html`, `404.html`, `closed-testing.html` | `legal/*.mjs` | `npm run legal` (o `npm run build`) |
| `store/**` (textos, CSV, capturas, `.ui-hash`, notas) | `store/listing.mjs` y la interfaz | `npm run store`, o `npm run release-notes` si solo cambian los textos |
| `assets/*.png`, iconos y pantallas de arranque de `android/`, `public/favicon.svg`, `logo-mark.svg`, `logo-light.svg` | `scripts/build-icons.mjs` | `npm run icons` |
| `www/` | todo lo demás | `npm run build` (no se versiona) |
| `public/logo-classic.svg` | es fijo | no lo regenera nadie |

## Antes de subir

1. `npm run typecheck`, `npm test` y `npm run build`.
2. Si cambias la interfaz o los textos: `npm run check:layout` (con `--stress` si tocas el editor de la ruleta y con `--theme=light` si tocas colores), y después `npm run store` y `npm run store:check`.
3. Pasa `npm run store:check` en toda PR a `main`, toque o no la interfaz a simple vista: la CI lo ejecuta y la huella cubre `index.html`, `src/` y los logos de `public/`, así que una PR con la huella vieja sale en rojo. Si falla, `npm run store` en una rama aparte.
4. Relee tu propio diff con ojo crítico: qué haría que la CI lo rechace.
5. No dejes ficheros temporales sin seguimiento dentro del repositorio (el hook de parada exige que todo esté commiteado). Los scripts de prueba van al directorio temporal de la sesión o a `node_modules/.cache`.
6. No subas credenciales, keystores ni `google-services.json`.

## Cuándo actuar y cuándo preguntar

Actúa sin preguntar cuando:
- Un fallo de CI es del propio cambio y tiene corrección clara y pequeña.
- Un comentario de revisión pide algo pequeño y local (un nombre, un texto, un test).
- Hay que regenerar un fichero generado.

Pregunta antes de:
- Tocar la política de privacidad, la sección «Seguridad de los datos», el compromiso de privacidad o las páginas legales (salvo para añadir un idioma ya acordado).
- Añadir permisos de Android (sobre todo `INTERNET`), SDK de terceros o scripts externos.
- Cambiar el formato de lo guardado (esquema, migraciones) o el identificador de una apariencia guardada (`calm`).
- Cambiar versión, nombre en clave o `versionCode`.
- Sobrescribir una rama remota, borrar ramas o reescribir historial.
- Desplegar (`npm run deploy`): publica en producción y es decisión del dueño. Solo se despliega desde `main` (lo exige `scripts/check-deploy.mjs`).
- Cualquier cosa que cambie fuera de la PR (Play Console, ajustes del repositorio).

## Esperar a la CI

No hagas sondeos con `sleep`: la suscripción a la PR avisa de los resultados. Durante una tarea larga (por ejemplo, regenerar la ficha de Play) no termines el turno a medias; espera a que acabe y haz un único commit completo.
